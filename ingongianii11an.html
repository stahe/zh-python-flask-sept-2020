    29. 应用练习：第11版

    29.1. 简介

    在税款计算客户端/服务器应用程序的先前版本中，实现该计算业务规则的 [métier] 层位于服务器端。现在我们计划将其移至客户端。 这样做有什么好处？服务器原先承担的工作将转移至客户端。设想一个由 N 个客户端查询的服务器，N 项税务业务计算将由客户端完成。在之前的版本中，这些 N 项业务计算均由服务器完成。由于不再执行业务计算，服务器将更快地响应客户端请求，从而能够同时服务更多的客户端。

    客户端/服务器架构如下：

    • [métier] [10] 层已在客户端复制为 [12]；
    • 客户端新增了脚本 [main2] [11]；

    Web客户端将有两种方式来计算[3]中找到的纳税人列表的税款：

    • 使用上一版本的方法。该方法利用服务器端的 [métier] 和 [10] 层。脚本 [main] 将采用此方法；
    • 仅向服务器请求税务管理数据（[2-4]），然后使用客户端本地的 [métier] 和 [12] 层；

    我们将对比这两种方法的性能。

    29.2. Web 服务器

    Web 服务器的目录结构如下：

    • 文件 [http-servers/06] 最初是通过复制文件 [http-servers/05] 生成的。 实际上，我们将保留前一版本（10版）的既有成果，仅在此基础上新增一项功能。该功能体现在新增的控制器 [get_admindata_controller] [1] 上。 另一个控制器[calculate_tax_controller]，其实就是旧控制器[index_controller]更名后的版本；

    29.3. 配置

    服务器将提供两个 URL 服务：

    • [/calculate-tax] 用于计算传递在 POST 主体中的纳税人列表的税款。 因此，它对应于先前第 10 版中的 URL [/]；
    • [/get-admindata] 生成税务管理数据链 jSON；

    配置 [config] 将上述每个 URL 与负责处理它的控制器关联起来：

    
    # Web 应用程序控制器字典
    import calculate_tax_controller, get_admindata_controller
    controllers = {"calculate-tax": calculate_tax_controller, "get-admindata": get_admindata_controller}
    config['controllers'] = controllers

    29.7. Web客户端

    29.9. 客户端测试

    在每个 [main, main2] 脚本中，我们都会记录脚本的开始和结束时间。这样就可以计算出脚本的执行时间。让我们做一些预测：

    • 上一版本的脚本 [main]：
      • 创建 N 个线程并同时执行；
      • 每个线程处理一批纳税人，并通过向服务器发送单次请求来计算其税款；
      • 由于 N 个线程同时运行，第 N+1 个请求会在第 N 个请求收到响应之前就被发起。因此，这 N 个请求的开销虽然高于单次请求，但可能不会高出太多。此外，服务器端还需进行 11 次（即纳税人数量）业务计算；
    • 该版本的脚本 [main2]：
      • 仅向服务器发起一次请求；
      • 在客户端本地执行11项业务计算；

    无论在服务器端还是客户端，业务计算所需的时间都是一样的。因此，差异主要体现在请求上。可以预期，[main]的执行时间会比[main2]稍长一些。

    我们启动版本 11 的服务器、SGBD 以及邮件服务器 [hMailServer]。在服务器端，我们将参数 [sleep_time] 设为零，以确保两项测试在相同条件下执行。
